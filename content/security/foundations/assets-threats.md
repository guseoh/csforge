# 자산·위협·취약점을 구분해 위험을 정의하기

보안을 “JWT를 쓴다”, “CORS를 켠다” 같은 기술 목록으로 시작하면 **무엇을 누구에게서 보호하는지**가 빠집니다. 먼저 자산(asset), 위협(threat), 취약점(vulnerability)을 구분해야 방어가 필요한 이유를 설명할 수 있습니다.

주문 서비스의 예를 보겠습니다.

```text
보호할 자산
├─ 회원 계정
├─ 결제 정보
├─ 주문 상태
└─ 관리자 기능

공격자가 원하는 결과
├─ 다른 회원 주문 조회
├─ 결제 상태 위조
└─ 관리자 권한 획득

가능하게 하는 취약점
├─ 소유권 검사 없음
├─ 서버가 클라이언트 상태를 그대로 신뢰
└─ 관리자 엔드포인트 권한 검사 누락
```

### 같은 취약점도 자산에 따라 위험이 달라진다

디버그 엔드포인트가 내부 빌드 버전만 보여주는 것과 DB 자격 증명을 보여주는 것은 같은 정보 노출이라도 영향이 다릅니다. 위험은 공격 가능성과 영향 범위를 함께 살펴 판단합니다.

### 위협은 구체적인 실행 경로로 적는다

“인가가 약하다”보다 다음처럼 적으면 검증할 수 있습니다.

```text
공격자: 로그인한 일반 사용자
전제: 주문 ID를 추측할 수 있음
행동: GET /orders/{otherUserOrderId}
취약점: 컨트롤러가 ID만 조회하고 소유권을 검사하지 않음
결과: 다른 사용자의 주문 정보 노출
```

이렇게 위협 상황을 만들면 필요한 방어도 분명해집니다. ID를 숨기는 것만이 아니라 **서버에서 현재 인증 주체와 리소스 소유자를 비교**해야 합니다.

### 보안은 실패 경로 설계이기도 하다

공격 요청을 막는 것만으로 끝나지 않습니다. 인증 실패와 인가 실패를 구분하고, 로그에는 분석 정보만 남기되 비밀번호와 토큰 원문은 제외해야 합니다. 요청 속도 제한이 정상 사용자를 과도하게 차단하지 않는지도 확인합니다.

좋은 보안 설계는 “기술을 많이 넣었다”가 아니라 **어떤 자산에 어떤 공격 경로가 있고, 어느 경계에서 어떤 검사가 그 경로를 끊는지**를 설명할 수 있는 상태입니다.
