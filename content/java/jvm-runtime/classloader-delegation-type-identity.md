# 이름이 같은 class가 왜 서로 다른 타입이 될 수 있을까

애플리케이션과 plugin이 모두 `com.example.Service`라는 class를 가지고 있다고 해 보겠습니다. package와 class 이름이 완전히 같으니 JVM도 같은 타입으로 볼 것 같지만, 실제 runtime type identity에는 **그 class를 정의한 ClassLoader**도 중요합니다.

이 원리를 모르고 plugin, application server, hot reload 환경을 다루면 `ClassCastException`이 "같은 클래스끼리 왜 cast가 안 되지?"처럼 보일 수 있습니다.

### ClassLoader는 class의 binary representation을 찾아 JVM에 정의한다

Java에서 class를 사용할 때 class loader는 binary name에 해당하는 class definition을 찾습니다.

```text
binary name
"com.example.Service"
        │
        ▼
   ClassLoader
        │ class bytes
        ▼
   runtime Class
```

`ClassLoader` 객체가 모두 같은 방식으로 jar만 읽는 것은 아닙니다. custom loader는 네트워크, plugin directory, generated byte array 등 다른 source에서 class를 정의할 수도 있습니다.

### parent delegation은 먼저 상위 loader에게 물어보는 일반적인 구조다

`ClassLoader.loadClass`의 일반적인 기본 동작은 이미 load됐는지 확인하고 parent loader에게 먼저 요청한 뒤 필요하면 자신이 찾는 형태입니다.

```text
Application ClassLoader
        │
        ├─ parent에게 요청
        ▼
Platform/Bootstrap 쪽
        │
        └─ 찾지 못하면 child가 자신의 class 검색
```

이 방식은 Java platform class나 공통 library가 loader마다 제각각 중복 정의되는 문제를 줄입니다.

하지만 모든 custom loader가 무조건 같은 parent-first 전략을 써야 하는 것은 아닙니다. plugin/container 환경은 child-first나 별도 loader graph를 사용할 수 있습니다. **delegation은 ClassLoader API와 구체적인 loader 구현 계약을 함께 확인**해야 합니다.

### runtime type은 binary name만으로 결정되지 않는다

두 loader가 각각 같은 binary name의 class를 정의한다고 해 보겠습니다.

```text
Loader A ──define──▶ com.example.Plugin
Loader B ──define──▶ com.example.Plugin
```

이 두 class는 이름 문자열은 같아도 서로 다른 runtime type이 될 수 있습니다.

```java
Class<?> a = loaderA.loadClass("com.example.Plugin");
Class<?> b = loaderB.loadClass("com.example.Plugin");

System.out.println(a.getName().equals(b.getName())); // true일 수 있음
System.out.println(a == b);                         // false일 수 있음
```

그래서 loader A가 정의한 `Plugin` instance를 loader B가 정의한 `Plugin`으로 cast할 수 없을 수 있습니다.

```text
same binary name
      +
different defining loader
      =
different runtime type identity
```

### "같은 interface를 공유"하려면 loader 경계가 중요하다

Plugin system에서 host와 plugin이 협력하려면 보통 공통 API interface는 **둘이 공유하는 상위 loader**에서 정의하고, plugin 구현 class만 plugin별 loader에서 읽게 하는 구조를 사용합니다.

```text
Parent Loader
   └─ PluginApi interface
          ▲
          │ implements
 ┌────────┴────────┐
Plugin Loader A  Plugin Loader B
   ImplA             ImplB
```

만약 각 plugin loader가 `PluginApi` interface까지 따로 정의한다면 source상 같은 interface여도 runtime에서는 서로 다른 타입이 되어 host가 구현체를 받기 어려워집니다.

이것이 class loader 설계가 단순한 "파일 찾기" 이상의 의미를 가지는 이유입니다.

### `getClassLoader()`는 이상한 cast 문제를 진단하는 단서가 된다

```java
System.out.println(object.getClass());
System.out.println(object.getClass().getClassLoader());
```

이름이 같은 두 class가 충돌할 때는 다음을 확인합니다.

- 실제 `Class` 객체가 같은가
- defining ClassLoader가 같은가
- 어느 jar/path에서 class bytes가 왔는가
- parent delegation 구조가 어떻게 되어 있는가

Spring Boot devtools, application server, plugin framework처럼 class loader가 여러 개인 환경에서 특히 유용합니다.

### ClassLoader와 classpath를 같은 것으로 보면 안 된다

Classpath는 class를 찾을 수 있는 source를 구성하는 한 방식입니다. ClassLoader는 runtime에서 class definition을 찾고 정의하는 객체와 규칙입니다.

```text
classpath/module path -> class를 찾는 source/configuration
ClassLoader           -> runtime loading/definition 주체
```

따라서 "classpath에 같은 jar가 있다"만으로 실제 defining loader가 같다고 결론내릴 수 없습니다.

### class가 unload되려면 loader 생명주기도 중요하다

특정 class만 "이제 안 쓰니 unload"한다고 간단히 지우는 모델이 아닙니다. JVM 구현에서 class unloading을 생각할 때는 그 class를 정의한 loader와 관련 class들이 더 이상 reachable하지 않은지 같은 loader 생명주기가 중요합니다.

Plugin reload나 application redeploy에서 이전 ClassLoader를 static cache나 thread가 계속 참조하면 class metadata가 오래 남는 문제로 이어질 수 있습니다.

세부 unloading 정책은 JVM implementation 영역이므로 "method가 끝나면 class가 unload된다"고 설명하지 않습니다.

### 문제를 풀 때 확인할 것

1. class의 binary name만 보지 말고 defining loader를 확인합니다.
2. parent delegation 구조를 그립니다.
3. 공통 interface가 어느 loader에서 정의됐는지 봅니다.
4. source/jar가 같다는 것과 runtime `Class` identity가 같다는 것을 구분합니다.
5. cast 실패 시 `getClassLoader()`를 진단 단서로 사용합니다.
6. custom loader가 반드시 parent-first라고 가정하지 않습니다.

### 면접에서 설명한다면

ClassLoader는 runtime에서 class definition을 찾고 JVM에 정의합니다. 일반적인 loader는 parent delegation으로 상위 loader에 먼저 요청하지만 custom loader는 다른 정책을 가질 수 있습니다. JVM의 runtime type identity에는 binary name뿐 아니라 defining ClassLoader도 중요해서, 같은 이름의 class라도 서로 다른 loader가 정의하면 다른 타입이 될 수 있습니다. 그래서 plugin이나 application server에서는 공통 API를 어떤 loader가 정의하는지가 중요합니다.
