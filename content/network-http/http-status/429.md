# 요청 제한과 429

`429 Too Many Requests`는 서버가 사용하는 요청률 제한 정책에서 한 주체가 일정 시간 동안 너무 많은 요청을 보냈다고 판단했을 때 쓰는 상태 코드다. HTTP 표준은 주체를 IP 주소, 인증 정보, 쿠키 중 무엇으로 식별할지, 요청을 어떤 시간 구간으로 셀지까지 정하지 않는다. 이 부분은 서버 정책이 정의한다.

따라서 429를 받았다고 `한 IP에서 초당 N회 제한`처럼 특정 알고리즘을 추측하면 안 된다. 사용자별·리소스별·서버 전체 또는 여러 서버를 묶은 제한 장치 등 다양한 정책이 같은 상태 코드를 사용할 수 있다.

### Retry-After는 재시도 시점을 알려 줄 수 있다

429 응답에는 `Retry-After` 필드를 넣어 클라이언트가 언제 다시 시도할 수 있는지 알려 줄 수 있다. 하지만 이 필드는 선택 사항이므로 없다고 해서 즉시 반복 요청을 보내도 된다는 뜻은 아니다.

```text
요청이 몰림
    ↓
요청률 제한 정책 초과
    ↓
429 Too Many Requests
    └─ 선택적 Retry-After 필드
```

429와 `503 Service Unavailable`도 구분해야 한다. 429는 특정 요청 주체의 요청률이 정책을 넘었다는 뜻이고, 503은 서비스가 현재 요청을 처리할 수 없는 일시적인 상태를 나타낸다.

또한 RFC 6585는 429 응답을 캐시에 저장하지 않도록 규정한다. 핵심은 **429가 전송 오류가 아니라 서버의 요청률 정책이 현재 요청을 받아들이지 않는다는 HTTP 수준의 피드백**이라는 점이다.
