# 게이트웨이의 중계 역할

클라이언트가 하나의 공개 API에 요청하더라도 내부에서는 여러 서비스가 각자 다른 경로나 프로토콜로 동작할 수 있습니다. HTTP 게이트웨이는 클라이언트 쪽에서 원본 서버처럼 요청을 받아 내부의 다른 서버로 전달하는 중개자입니다. HTTP 문맥에서는 역방향 프록시라고도 부릅니다.

예를 들어 공개 GET /api/products 요청을 내부 상품 서비스에 전달하고, 다른 요청은 재고 서비스로 보낼 수 있습니다. HTTP 요청을 내부 gRPC 호출로 변환하는 게이트웨이도 있습니다. 외부 요청과 내부 호출은 별도의 메시지·연결 계약을 갖습니다.

### 정책을 적용하는 경계

API 게이트웨이는 경로 선택 외에 인증, 요청률 제한, 타임아웃, 로그 등을 담당할 수 있습니다. 모든 기능이 HTTP 게이트웨이에 필수인 것은 아니며, 실제 요구사항에 따라 역방향 프록시와 애플리케이션이 역할을 나눌 수 있습니다.

가령 게이트웨이가 인증된 사용자 ID를 내부로 전달한다면 외부 클라이언트가 같은 헤더에 임의 값을 넣지 못하게 해야 합니다. 백엔드의 직접 접근 경로를 제한하고 신뢰된 채널인지 확인한 뒤에도 리소스별 인가는 별도로 수행해야 합니다.

### 실패를 해석하는 방법

게이트웨이가 백엔드에 요청을 보냈다고 업무 처리가 성공한 것은 아닙니다. 상위 서버가 잘못된 응답을 제공하면 502, 제시간에 응답하지 않으면 504 등 중개자 관점의 오류가 발생할 수 있습니다. 백엔드가 이미 변경을 커밋한 뒤 응답만 유실됐을 수도 있으므로 상태 변경 요청을 무조건 재시도해서는 안 됩니다.

게이트웨이를 도입할 때는 이름보다 실제로 끝나는 연결, 변환하는 프로토콜, 적용하는 신뢰 정책 및 실패 책임을 먼저 정의하는 것이 중요합니다.
