# 304 Not Modified

`304 Not Modified`는 conditional GET 또는 HEAD가 조건이 없었다면 `200 OK`가 되었겠지만, precondition이 false로 평가되어 target representation의 content를 다시 전송할 필요가 없을 때 사용하는 response다. recipient가 이미 유효한 stored representation을 가지고 있다는 전제에서 그 representation을 재사용하게 한다. 따라서 304는 임의의 “변경 없음” application status가 아니며 GET/HEAD conditional request의 protocol 결과다.

**304 response에는 content가 없다.** server는 같은 request에 200을 보냈다면 포함했을 `Content-Location`, `Date`, `ETag`, `Vary`와 cache 정책에 해당하는 `Cache-Control`, `Expires`를 304에서도 생성해야 한다. 그 밖의 representation metadata는 cache update에 실제로 필요하지 않다면 정보 전송을 줄이기 위해 생략하는 것이 권장된다.

cache는 304를 받으면 validation에 사용한 stored response의 content를 그대로 유지하면서 304가 제공한 metadata로 entry를 갱신한 뒤 재사용할 수 있다. 반대로 client가 validator만 가지고 있고 실제 stored representation을 잃어버렸다면 304만으로 body를 복원할 수 없다. cache entry가 없으면 conditional request를 보내지 않거나 full representation을 다시 받아야 한다.

304를 반환하기 전에 target resource와 selected representation, authorization·tenant scope를 올바르게 결정해야 한다. validator match는 permission check를 대신하지 않으며, GET/HEAD가 아닌 method의 `If-None-Match`가 false가 되는 경우에는 304가 아니라 412 같은 precondition semantics를 적용한다.

### Backend 연결

Spring controller와 proxy가 304에 JSON serializer나 response content를 붙이지 않는지, 그리고 ETag·Vary·Cache-Control 같은 metadata가 대응하는 200 response와 같은 representation contract를 가리키는지 검증한다. user-specific response에서는 validator가 같다는 이유만으로 다른 tenant의 cached body를 재사용하지 않도록 cache scope와 resource selection을 먼저 고정한다.
