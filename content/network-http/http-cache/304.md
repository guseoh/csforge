# 304 Not Modified

`304 Not Modified`는 조건부 GET 또는 HEAD에서 validator가 현재 selected representation과 일치해 response content를 다시 보낼 필요가 없다는 상태다. server나 intermediary가 304를 보내면 client는 이미 저장한 representation의 body와 304의 갱신 가능한 metadata를 결합해 최종 response를 구성한다. 304는 “server가 아무것도 하지 않았다”는 뜻이 아니라, 조건 평가가 성공해 body 전송만 생략되었다는 뜻이다.

304 response에는 일반적으로 response body가 없으며, 새 JSON body를 담아 보내는 API 성공 응답으로 취급해서는 안 된다. cache는 `ETag`, `Cache-Control`, `Expires` 같은 허용된 metadata를 저장된 response에 반영할 수 있다. 그러나 client의 body가 삭제되었거나 요청 representation variant가 달라 저장된 entry를 사용할 수 없다면 304만으로 복원할 수 없으므로, cache는 일반 요청을 다시 수행하거나 304를 생성하지 않아야 한다.

304는 조건부 GET/HEAD의 의미를 벗어나 임의의 “변경 없음” 응답으로 사용하지 않는다. `If-None-Match`가 일치하거나 `If-Modified-Since` 조건에 맞을 때만 선택하고, method와 precondition에 따라 412가 되어야 하는 경우와 구분한다. 또한 response가 304로 짧아졌더라도 resource 조회와 authorization을 건너뛰면 validator가 보호해야 할 표현의 존재나 범위를 잘못 노출할 수 있다.

### Backend 연결

Spring controller와 proxy가 304에 JSON serializer나 body를 붙이지 않고, `Content-Encoding`·ETag·cache metadata를 해당 representation과 일관되게 처리하는지 검증한다. ETag match 뒤에도 권한과 tenant scope를 먼저 확인하고, client가 body를 갖고 있지 않은 경우 304가 빈 화면으로 끝나지 않도록 일반 GET fallback을 둔다.
